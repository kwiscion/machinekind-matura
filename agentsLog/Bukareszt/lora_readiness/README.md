## Deviations and pins (none relaxed)

- **python3-venv is missing on the host.** Instead of changing system packages, I used a project-local `uv` 0.12.19 in `/ephemeral/mm-lora/bin`. Python 3.12.14 is uv-managed; the Python version was not pinned by the RUNBOOK. Root's Windows installs evidently used ≥3.11, since its freeze has networkx 3.6.1.
- **uv rejects extensionless codeload URLs.** The same exact-commit archives were downloaded first, hash-checked against root's values, and installed from `file://`. `direct_url.json` therefore records the file path. `probe_linux.py` re-verifies the archive SHAs and installed source hashes, which is stronger than the URL string check in root's Windows-only `run_cpu_probe.py`.
- **Converter dependency conflict.** llama.cpp `fcb3074f` `requirements-convert_hf_to_gguf.txt` pins `transformers==4.57.6`, which cannot load the Gemma 4 tokenizer config (`AttributeError: 'list' object has no attribute 'keys'` on `extra_special_tokens`). The text conversion failed with it; the projector conversion succeeded. `venv-convert-pinned` keeps llama.cpp's own requirements (torch 2.11.0+cpu, numpy 2.2.6, protobuf 4.25.9, sentencepiece 0.2.2) and overrides **only** transformers with the RUNBOOK-pinned `96331a9f` archive. The converters use the repo's local `gguf-py` at the pinned commit (`NO_LOCAL_GGUF` unset).
- **`host_scripts/export_control2.sh` now fails closed**: `set -euo pipefail`, a required fresh output directory, a non-empty check on each artifact, and hashes. The historical run used `set -u` and continued past failures; its outputs were verified separately by hash.
- `llama-quantize` was built CPU-only with cmake/ninja from PyPI in `venv-tools`.
- The RUNBOOK example writes the projector to `--outfile projector.gguf`. At this commit the emitted name is exactly `projector.gguf`, with no automatic `mmproj-` prefix.

## Blockers and next steps (for root's launch declaration)

1. **Full 12B attach/backward/memory.** The next finite step is one declared real-model synthetic backward on the GPU venv: BF16 base, 88 modules, finite loss/grad, peak memory. It needs root's declaration, because it loads the model and runs a forward pass.
2. **Adapter serving is unproven.** The GGUF adapter converts, but loading it (llama.cpp `--lora` / Ollama `ADAPTER`) together with the matching base, enable/disable switching, and unchanged image routes all require inference calls. The single-merged-model path needs the same offline load plus the all-route regression.
3. **Pipeline drift.** Our llama.cpp Q4_K_M control is not byte-identical to the registry Q4 that scored 35/60: every quantized tensor differs, while F32 and projector data are identical. Before crediting any LoRA effect, a matched control-vs-registry comparison is required, as the RUNBOOK anticipates. Alternatively, export the candidate through the same quantizer that produced the registry blob, if that can be identified.
4. The real `essay_lora_clearance_v1` sidecar binding the 90 rows and eval16 must be issued by the independent reviewer (root). I did not hand-mark it.
