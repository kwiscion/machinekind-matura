# Gemma vision resolution readiness — 26 September 2026

Recommendation: do not spend a full arm on doubling page DPI alone. The installed backend's default preprocessing maps both the current 910×1287 page and a roughly doubled 220-DPI render to **672×912 pixels / 266 visual tokens**. Higher source DPI can change antialiasing and sampled pixel values, but does not itself increase the model's spatial token budget. Any score gain from that limited effect is unmeasured.

- In that exact [backend's projector initialization](https://github.com/ggml-org/llama.cpp/blob/6f3a9f3dee3c27545371044a3a38005721ac8a8e/tools/mtmd/clip.cpp), Gemma4 unified multiplies patch size 16 by default merge factor 3, yielding 48, then sets merge to 1. Bilinear resize and default image-token limits 40–280 apply. Local projector metadata has no scale-factor override.
- [Pixel-budget conversion](https://github.com/ggml-org/llama.cpp/blob/6f3a9f3dee3c27545371044a3a38005721ac8a8e/tools/mtmd/clip-model.h) gives maximum `280 × 48² = 645120` pixels. [Gemma4 unified selects the dynamic-size processor](https://github.com/ggml-org/llama.cpp/blob/6f3a9f3dee3c27545371044a3a38005721ac8a8e/tools/mtmd/mtmd.cpp), whose [resize calculation](https://github.com/ggml-org/llama.cpp/blob/6f3a9f3dee3c27545371044a3a38005721ac8a8e/tools/mtmd/mtmd-image.cpp) scales over-budget images down and floors both axes to multiples of 48. CPU arithmetic reproduced **672×912** for 910×1287, 1820×2574, and 1820×2573; `14 × 19 = 266` visual tokens per page, excluding boundary markers. This is calculated preprocessing behavior, not a new inference measurement.
- The existing [runner](../../infer.py) sends the original image bytes as data URLs and has no explicit resize/detail control. Google documents a separate [visual-token-budget control](https://ai.google.dev/gemma/docs/capabilities/vision/image) for variable resolution. Increasing source DPI is not equivalent to increasing that budget. Its Transformers example does not establish an available Ollama request option.

The command-line and pinned-source evidence strongly support the default calculation. A targeted read of only image-budget environment overrides was blocked by OS permissions on the service's `/proc/.../environ`; no privilege change was attempted. Therefore an unseen environment override is not excluded, and actual post-resize pixels/tensors were not captured. For any fixed cap already exceeded by these pages, doubling DPI at the same aspect ratio still preserves the cap and nearly the same target dimensions. It does not imply bit-identical tensors: rasterization and subsequent interpolation can differ.

The lead supplied effective context **4096**, largest observed policy prompt **1677**, and **13 two-page items**. With the unchanged 1024-output cap, the observed maximum leaves `4096 − 1677 − 1024 = 1395` tokens. This is observed headroom, not proof that a higher visual budget fits every item. The model metadata's 262144 architecture limit is not the active context. Changing visual-token budget would be a separate runtime/configuration experiment and needs fresh context accounting.
